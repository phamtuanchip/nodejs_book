Chương 15: REST API Best Practices và API Design

Viết API chạy được chỉ mất vài phút. Viết API mà người khác (và tương lai bạn) thực sự muốn dùng đòi hỏi kiến thức về thiết kế. Chương này dạy các quy ước và patterns được cả thế giới dùng.

🎯 Sau chương này bạn sẽ hiểu được
  • Đặt tên resources đúng REST conventions
  • Dùng HTTP status codes đúng ngữ cảnh
  • Implement pagination, filtering, sorting chuẩn
  • Versioning API đúng cách
  • Document API với Swagger/OpenAPI
  • Upload file với Multer

15.1 REST Conventions — Đặt tên đúng

REST (Representational State Transfer) không phải là một chuẩn kỹ thuật cứng nhắc — đây là một tập hợp các quy ước được cộng đồng lập trình thế giới đồng thuận và áp dụng rộng rãi. Khi bạn đặt tên URL theo đúng REST conventions, mọi developer khác đều có thể đoán ra ý nghĩa của endpoint mà không cần đọc tài liệu.

Resources là danh từ số nhiều

Nguyên tắc cốt lõi nhất của REST: URL biểu diễn resource (tài nguyên), không phải action (hành động). Hành động được biểu diễn bằng HTTP method (GET, POST, PUT, DELETE). Vì vậy URL chỉ chứa danh từ, không chứa động từ.

Tại sao dùng số nhiều? Vì resource collection (tập hợp) về mặt khái niệm luôn ở dạng số nhiều. /users là tập hợp tất cả users, /users/5 là user số 5 trong tập hợp đó. Nhất quán với số nhiều giúp URL dễ đoán hơn.

So sánh SAI vs ĐÚNG

SAI ❌ (có động từ) ĐÚNG ✅ (REST convention) Giải thích
GET /getUsers GET /users GET đã nói lên "lấy", không cần "get" trong URL
POST /createUser POST /users POST đã nói lên "tạo mới", resource là /users
PUT /updateUser/5 PUT /users/5 PUT đã nói lên "cập nhật", :id xác định resource cụ thể
DELETE /deleteUser/5 DELETE /users/5 DELETE đã nói lên "xóa", không cần thêm động từ
GET /getUserPosts/5 GET /users/5/posts Nested resource thể hiện quan hệ cha-con rõ ràng

Nested Resources — Biểu diễn quan hệ cha-con

Khi một resource thuộc về một resource khác, dùng URL lồng nhau để thể hiện quan hệ đó. Tuy nhiên không nên lồng quá 2-3 cấp vì URL sẽ trở nên dài và khó đọc.

Ví dụ: /users/42/posts/7/comments — đây là comments của bài post số 7, thuộc user số 42. Nếu cần đi sâu hơn, hãy cân nhắc tạo endpoint phẳng hơn thay vì lồng thêm.

💡 Mẹo
Khi bạn không chắc một action có phù hợp với REST không (ví dụ: "activate account", "send email"), hãy nghĩ về nó như một resource. POST /users/:id/activation hoặc POST /emails/send — biến action thành resource phụ là cách phổ biến nhất.
📌 Ghi nhớ
Dùng kebab-case cho URL nhiều từ: /blog-posts thay vì /blogPosts hay /blog_posts. Hầu hết các API lớn (GitHub, Stripe, Twilio) đều dùng kebab-case cho URL và camelCase cho JSON body/response.

15.2 HTTP Status Codes — Dùng đúng ngữ cảnh

HTTP status codes là ngôn ngữ chung giữa server và client. Khi bạn trả về đúng status code, client (trình duyệt, mobile app, hay service khác) biết chính xác điều gì đã xảy ra mà không cần parse response body. Nhiều developer hay dùng 200 OK cho mọi thứ rồi nhét error vào body — đây là anti-pattern nghiêm trọng.

Code Tên Dùng khi nào Ví dụ thực tế
200 OK Request thành công, có data trả về GET /users trả danh sách users
201 Created Tạo resource mới thành công POST /users tạo user mới; body chứa user vừa tạo
204 No Content Thành công nhưng không có data trả về DELETE /users/5 xóa thành công, không cần body
301 Moved Permanently Resource đã đổi URL vĩnh viễn API v1 bị deprecated, chuyển hướng sang v2
302 Found Chuyển hướng tạm thời Sau login, chuyển về trang dashboard
400 Bad Request Request sai cú pháp / thiếu field bắt buộc POST /users thiếu field email trong body
401 Unauthorized Chưa xác thực (chưa đăng nhập) Gọi API không kèm token hoặc token sai
403 Forbidden Đã xác thực nhưng không có quyền User thường cố xóa tài khoản của admin
404 Not Found Resource không tồn tại GET /users/9999 — user ID 9999 không có trong DB
409 Conflict Conflict với trạng thái hiện tại của resource POST /users với email đã tồn tại trong hệ thống
422 Unprocessable Entity Cú pháp đúng nhưng dữ liệu không hợp lệ (validation fail) Email đúng format nhưng domain không tồn tại
429 Too Many Requests Client gửi quá nhiều request (rate limiting) Gọi API quá 100 lần/phút vượt giới hạn cho phép
500 Internal Server Error Lỗi không xác định phía server Unhandled exception, DB connection drop đột ngột
503 Service Unavailable Server tạm thời không phục vụ được Đang bảo trì, quá tải, hoặc dependency service sập
⚠️ Cảnh báo
Phân biệt rõ 401 vs 403: 401 có nghĩa "tôi không biết bạn là ai — hãy đăng nhập". 403 có nghĩa "tôi biết bạn là ai nhưng bạn không có quyền làm việc này". Nhầm lẫn hai mã này là lỗi phổ biến nhất khi implement auth middleware.

Một nguyên tắc hữu ích: nhóm theo chữ số đầu tiên. 2xx — thành công. 3xx — chuyển hướng. 4xx — lỗi do client (client phải sửa request). 5xx — lỗi do server (client không làm gì được, chờ server fix). Khi client nhận 4xx, họ biết cần sửa code của họ. Khi nhận 5xx, họ biết cần báo cáo lỗi.

15.3 Response Format Nhất Quán

Một trong những điều gây khó chịu nhất khi dùng API là mỗi endpoint lại có cấu trúc response khác nhau. Endpoint này trả { user: {...} }, endpoint kia trả thẳng object, endpoint nọ lại trả { result: true, payload: {...} }. Client phải handle từng trường hợp riêng — đây là design tệ.

Giải pháp: định nghĩa một response format nhất quán và dùng nó cho tất cả endpoints. Dưới đây là ví dụ về 3 loại response phổ biến nhất.

Success — Single Resource

JSONresponse-success.json
{
  "success": true,
  "message": "Lấy thông tin user thành công",
  "data": {
    "id": "64a1b2c3d4e5f6789012345",
    "name": "Nguyễn Văn An",
    "email": "an@example.com",
    "role": "user",
    "createdAt": "2024-01-15T08:30:00.000Z"
  }
}

Error Response

JSONresponse-error.json
{
  "success": false,
  "error": {
    "code": "USER_NOT_FOUND",
    "message": "Không tìm thấy user với ID đã cung cấp"
  }
}

List + Pagination

JSONresponse-list.json
{
  "success": true,
  "data": [
    { "id": "1", "name": "An", "email": "an@example.com" },
    { "id": "2", "name": "Bình", "email": "binh@example.com" }
  ],
  "pagination": {
    "page": 1,
    "limit": 10,
    "total": 87,
    "totalPages": 9,
    "hasNext": true,
    "hasPrev": false
  }
}

Để đảm bảo tính nhất quán, tạo một module helper chứa tất cả các hàm format response. Mọi route handler chỉ gọi hàm từ module này thay vì tự viết res.json(). 

JavaScripthelpers/apiResponse.js
// helpers/apiResponse.js
const success = (res, data, message = 'Thành công', statusCode = 200) => {
  return res.status(statusCode).json({ success: true, data, message });
};

const created = (res, data, message = 'Tạo thành công') => {
  return res.status(201).json({ success: true, data, message });
};

const paginated = (res, data, pagination) => {
  return res.status(200).json({ success: true, data, pagination });
};

const error = (res, message, code, statusCode = 400) => {
  return res.status(statusCode).json({ success: false, error: { code, message } });
};

module.exports = { success, created, paginated, error };

Và cách dùng trong các route handler: 

JavaScriptroutes/users.js
const apiResponse = require('../helpers/apiResponse');

// GET /users/:id
router.get('/:id', asyncHandler(async (req, res) => {
  const user = await User.findById(req.params.id).lean();
  if (!user) {
    return apiResponse.error(res, 'Không tìm thấy user', 'USER_NOT_FOUND', 404);
  }
  return apiResponse.success(res, user, 'Lấy thông tin user thành công');
}));

// POST /users
router.post('/', asyncHandler(async (req, res) => {
  const existing = await User.findOne({ email: req.body.email });
  if (existing) {
    return apiResponse.error(res, 'Email đã tồn tại', 'EMAIL_CONFLICT', 409);
  }
  const user = await User.create(req.body);
  return apiResponse.created(res, user, 'Tạo user thành công');
}));
📌 Ghi nhớ
Trường error.code là machine-readable string (ví dụ: USER_NOT_FOUND, EMAIL_CONFLICT). Client có thể switch-case trên đây để hiển thị thông báo lỗi phù hợp với ngôn ngữ của user mà không cần parse message (vốn có thể thay đổi).

15.4 Pagination — Phân trang

Không bao giờ trả về toàn bộ collection trong một request. Nếu database có 1 triệu records, trả về tất cả trong một lần sẽ làm sập server và timeout client. Có hai chiến lược phân trang phổ biến: offset pagination và cursor pagination.

Offset Pagination (Trang theo số thứ tự)

Đây là cách đơn giản nhất và quen thuộc nhất: user yêu cầu "trang số N, mỗi trang M items". Phù hợp khi người dùng cần nhảy tới một trang cụ thể (ví dụ: "đi tới trang 5"). Nhược điểm: hiệu suất kém khi offset lớn vì DB phải scan và bỏ qua nhiều rows. 

JavaScriptmiddleware/paginate.js
// middleware/paginate.js
const paginate = (req) => {
  const page = Math.max(1, parseInt(req.query.page) || 1);
  const limit = Math.min(100, Math.max(1, parseInt(req.query.limit) || 10));
  const skip = (page - 1) * limit;
  return { page, limit, skip };
};

// Usage in route
router.get('/posts', asyncHandler(async (req, res) => {
  const { page, limit, skip } = paginate(req);
  const [data, total] = await Promise.all([
    Post.find().skip(skip).limit(limit).lean(),
    Post.countDocuments()
  ]);
  const totalPages = Math.ceil(total / limit);
  apiResponse.paginated(res, data, {
    page, limit, total, totalPages,
    hasNext: page < totalPages,
    hasPrev: page > 1
  });
}));

Chú ý Math.min(100, ...) — giới hạn tối đa 100 items/page để tránh client yêu cầu ?limit=999999 gây quá tải server. Luôn có giới hạn trên cho limit.

Cursor Pagination (Phân trang theo con trỏ)

Cursor pagination không dùng số trang mà dùng một "con trỏ" (thường là ID của item cuối cùng) để xác định điểm bắt đầu của trang tiếp theo. Đây là cách tiếp cận của Facebook, Twitter, Instagram — những nơi có feed vô hạn (infinite scroll). Hiệu suất tốt hơn offset rất nhiều vì DB có thể dùng index để tìm điểm bắt đầu. 

JavaScriptroutes/posts.js
router.get('/posts/cursor', asyncHandler(async (req, res) => {
  const { cursor, limit = 10 } = req.query;
  const query = cursor ? { _id: { $lt: cursor } } : {};
  const posts = await Post.find(query)
    .sort({ _id: -1 })
    .limit(parseInt(limit) + 1)
    .lean();
  const hasMore = posts.length > limit;
  if (hasMore) posts.pop();
  res.json({
    success: true,
    data: posts,
    nextCursor: hasMore ? posts[posts.length - 1]._id : null,
    hasMore
  });
}));

Trick quan trọng: query limit + 1 items. Nếu trả về đúng limit + 1 items, nghĩa là vẫn còn data (hasMore = true) và item cuối cùng bị pop ra làm nextCursor. Nếu trả về ít hơn hoặc bằng limit items, là trang cuối (hasMore = false).

💡 Mẹo
Chọn loại pagination nào? Nếu UI cần "Trang 1, 2, 3..." hoặc "Nhảy đến trang 50" → dùng offset. Nếu UI là infinite scroll (TikTok, Instagram feed, chat messages) → dùng cursor. Cursor nhanh hơn và không bị vấn đề "item bị skip hoặc lặp" khi có data mới insert trong lúc user đang phân trang.

15.5 Filtering, Sorting và Search

Sau khi đã implement pagination, bước tiếp theo là cho phép client lọc và sắp xếp data. Tất cả filtering parameters được truyền qua query string. Ví dụ:

  • GET /products?category=electronics&minPrice=100&maxPrice=500 — lọc theo category và giá
  • GET /products?sort=price&order=asc — sắp xếp theo giá tăng dần
  • GET /products?q=macbook — full-text search theo từ khóa
  • GET /products?fields=id,name,price — chỉ lấy các fields cần thiết (field selection)

Thay vì viết logic lặp đi lặp lại ở mỗi route, hãy tách ra thành một helper function: 

JavaScripthelpers/buildMongoQuery.js
// helpers/buildMongoQuery.js
const buildMongoQuery = (queryParams) => {
  const { q, category, minPrice, maxPrice, inStock, sort, order, fields } = queryParams;
  const filter = {};

  if (q) filter.$text = { $search: q };
  if (category) filter.category = category;
  if (minPrice || maxPrice) {
    filter.price = {};
    if (minPrice) filter.price.$gte = Number(minPrice);
    if (maxPrice) filter.price.$lte = Number(maxPrice);
  }
  if (inStock !== undefined) filter.inStock = inStock === 'true';

  // Sort: ?sort=price&order=asc hoặc ?sort=-price
  let sortObj = { createdAt: -1 };
  if (sort) {
    const sortField = sort.startsWith('-') ? sort.slice(1) : sort;
    const sortDir = sort.startsWith('-') ? -1 : (order === 'desc' ? -1 : 1);
    sortObj = { [sortField]: sortDir };
  }

  // Field selection: ?fields=id,name,email
  let projection = null;
  if (fields) {
    projection = fields.split(',').reduce((acc, f) => ({ ...acc, [f.trim()]: 1 }), {});
  }

  return { filter, sortObj, projection };
};

module.exports = buildMongoQuery;

Và cách dùng helper trong route: 

JavaScriptroutes/products.js
const buildMongoQuery = require('../helpers/buildMongoQuery');
const { paginate } = require('../middleware/paginate');

router.get('/', asyncHandler(async (req, res) => {
  const { filter, sortObj, projection } = buildMongoQuery(req.query);
  const { page, limit, skip } = paginate(req);

  let query = Product.find(filter).sort(sortObj).skip(skip).limit(limit);
  if (projection) query = query.select(projection);

  const [data, total] = await Promise.all([
    query.lean(),
    Product.countDocuments(filter)
  ]);

  const totalPages = Math.ceil(total / limit);
  apiResponse.paginated(res, data, {
    page, limit, total, totalPages,
    hasNext: page < totalPages,
    hasPrev: page > 1
  });
}));
⚠️ Cảnh báo
Luôn whitelist các fields được phép filter/sort. Nếu client có thể sort theo bất kỳ field nào, họ có thể sort theo field không có index, gây full table scan và làm chậm toàn bộ hệ thống. Hãy kiểm tra sort chỉ nằm trong danh sách ['price', 'name', 'createdAt', 'rating'] trước khi áp dụng.
📌 Ghi nhớ
Để dùng full-text search với $text, MongoDB cần có text index trên các fields muốn search. Thêm vào Mongoose schema: ProductSchema.index({ name: 'text', description: 'text' }); Nếu không có index, query sẽ báo lỗi "text index required".

15.6 API Versioning

Khi API của bạn đã có người dùng (internal teams, mobile apps, third-party clients), bạn không thể đột ngột thay đổi response format hay xóa fields — điều đó sẽ break ứng dụng của họ. Đây là lúc cần API versioning.

Ba chiến lược versioning phổ biến

  • URL versioning: /api/v1/users, /api/v2/users — rõ ràng nhất, dễ test, được dùng nhiều nhất
  • Header versioning: Accept: application/vnd.myapi.v2+json — "sạch" hơn về mặt REST nhưng khó test với browser
  • Query param versioning: /api/users?version=2 — linh hoạt nhưng dễ bị quên, ít phổ biến

Với Express, URL versioning được implement bằng cách mount các router riêng biệt: 

JavaScriptapp.js
// app.js
app.use('/api/v1', require('./routes/v1'));
app.use('/api/v2', require('./routes/v2'));
JavaScriptroutes/v1/users.js
// routes/v1/users.js
const express = require('express');
const router = express.Router();
const User = require('../../models/User');

// V1: chỉ trả về name và email
router.get('/', async (req, res) => {
  const users = await User.find().select('name email').lean();
  res.json({ success: true, data: users });
});

module.exports = router;
JavaScriptroutes/v2/users.js
// routes/v2/users.js
const express = require('express');
const router = express.Router();
const User = require('../../models/User');

// V2: thêm phone, avatar, createdAt và metadata
router.get('/', async (req, res) => {
  const users = await User.find().select('name email phone avatar createdAt').lean();
  res.json({
    success: true,
    data: users,
    _meta: { version: '2.0', deprecation: null }
  });
});

module.exports = router;

Deprecation Policy — Thông báo version cũ sắp bị xóa

Khi bạn ra v2, không nên xóa v1 ngay lập tức. Hãy thêm header Deprecation vào tất cả response của v1 để thông báo cho client biết họ cần migrate: 

JavaScriptmiddleware/deprecation.js
// middleware/deprecation.js — thêm vào tất cả v1 routes
const deprecationWarning = (req, res, next) => {
  res.set('Deprecation', 'true');
  res.set('Sunset', 'Sat, 01 Jan 2026 00:00:00 GMT');
  res.set('Link', '<https://api.example.com/v2>; rel="successor-version"');
  next();
};

module.exports = deprecationWarning;

// app.js
app.use('/api/v1', deprecationWarning, require('./routes/v1'));

15.7 File Upload với Multer

Multer là middleware phổ biến nhất để handle multipart/form-data trong Express — đây là content type được dùng khi upload file. Multer parse request, lưu file vào disk (hoặc memory), và gắn thông tin file vào req.file / req.files. 

BashTerminal
npm install multer
JavaScriptmiddleware/upload.js
// middleware/upload.js
const multer = require('multer');
const path = require('path');

const storage = multer.diskStorage({
  destination: (req, file, cb) => {
    cb(null, 'uploads/avatars/');
  },
  filename: (req, file, cb) => {
    const ext = path.extname(file.originalname);
    cb(null, `avatar-${req.user.id}-${Date.now()}${ext}`);
  }
});

const fileFilter = (req, file, cb) => {
  const allowed = ['image/jpeg', 'image/png', 'image/webp'];
  if (allowed.includes(file.mimetype)) {
    cb(null, true);
  } else {
    cb(new Error('Chỉ chấp nhận file JPEG, PNG hoặc WebP'), false);
  }
};

const upload = multer({
  storage,
  limits: { fileSize: 5 * 1024 * 1024 }, // 5MB
  fileFilter
});

module.exports = upload;

Sau khi có middleware, kết nối vào route. Lưu ý middleware upload.single('avatar') phải được đặt trước route handler: 

JavaScriptroutes/users.js
// routes/users.js
const upload = require('../middleware/upload');
const apiResponse = require('../helpers/apiResponse');

router.post('/:id/avatar',
  authenticate,
  upload.single('avatar'),
  asyncHandler(async (req, res) => {
    if (!req.file) {
      return apiResponse.error(res, 'Vui lòng chọn file', 'FILE_REQUIRED', 400);
    }
    const user = await User.findByIdAndUpdate(
      req.params.id,
      { avatar: `/uploads/avatars/${req.file.filename}` },
      { new: true }
    );
    apiResponse.success(res, { avatar: user.avatar }, 'Upload avatar thành công');
  })
);

Upload nhiều file cùng lúc

Multer cũng hỗ trợ upload nhiều file. Dùng upload.array('images', 5) để nhận tối đa 5 file từ field tên "images", hoặc upload.fields([...]) cho nhiều field khác tên: 

JavaScriptroutes/posts.js
// Upload nhiều ảnh cho một bài post

  authenticate,
  upload.array('images', 5),

      { $push: { images: { $each: imageUrls } } },
      { new: true }
    );
    apiResponse.success(res, { images: post.images }, `Upload ${req.files.length} ảnh thành công`);
  })
);

⚠️ Cảnh báo
Không lưu file trực tiếp trên server production vì file sẽ mất khi deploy lại hoặc server restart. Dùng cloud storage: AWS S3, Google Cloud Storage, hoặc Cloudinary (tiện nhất cho ảnh vì tự động resize/optimize). Package multer-s3 cho phép stream file thẳng lên S3 mà không cần lưu tạm.

Handle lỗi từ Multer

Multer throw lỗi riêng có type là MulterError. Cần bắt riêng để trả về thông báo lỗi có nghĩa cho client: 

JavaScriptmiddleware/errorHandler.js
const multer = require('multer');

const handleMulterError = (err, req, res, next) => {
  if (err instanceof multer.MulterError) {
    if (err.code === 'LIMIT_FILE_SIZE') {
      return res.status(400).json({
        success: false,
        error: { code: 'FILE_TOO_LARGE', message: 'File không được vượt quá 5MB' }
      });
    }
    if (err.code === 'LIMIT_FILE_COUNT') {
      return res.status(400).json({
        success: false,
        error: { code: 'TOO_MANY_FILES', message: 'Tối đa 5 file mỗi lần upload' }
      });
    }
  }
  // Lỗi từ fileFilter
  if (err.message === 'Chỉ chấp nhận file JPEG, PNG hoặc WebP') {
    return res.status(400).json({
      success: false,
      error: { code: 'INVALID_FILE_TYPE', message: err.message }
    });
  }
  next(err);
};

module.exports = handleMulterError;

15.9 Rate Limiting — Bảo vệ API khỏi bị lạm dụng

Một API không có rate limiting là API không an toàn. Không có giới hạn, client có thể gửi hàng nghìn request mỗi giây, làm sập server hoặc tốn chi phí database/cloud của bạn. Package express-rate-limit là giải pháp đơn giản và hiệu quả nhất: 

BashTerminal
npm install express-rate-limit
JavaScriptmiddleware/rateLimiter.js
const rateLimit = require('express-rate-limit');

// General rate limiter: 100 requests per 15 minutes
const generalLimiter = rateLimit({
  windowMs: 15 * 60 * 1000, // 15 phút
  max: 100,
  message: {
    success: false,
    error: {
      code: 'RATE_LIMIT_EXCEEDED',
      message: 'Quá nhiều request. Vui lòng thử lại sau 15 phút.'
    }
  },
  standardHeaders: true,  // Thêm RateLimit-* headers
  legacyHeaders: false
});

// Strict limiter cho auth endpoints
const authLimiter = rateLimit({
  windowMs: 60 * 60 * 1000, // 1 giờ
  max: 10, // Chỉ 10 lần login thất bại mỗi giờ
  message: {
    success: false,
    error: {
      code: 'AUTH_RATE_LIMIT',
      message: 'Quá nhiều lần đăng nhập thất bại. Vui lòng thử lại sau 1 giờ.'
    }
  }
});

module.exports = { generalLimiter, authLimiter };

// app.js
const { generalLimiter, authLimiter } = require('./middleware/rateLimiter');
app.use('/api/', generalLimiter);
app.use('/api/v1/auth', authLimiter);

Khi request bị block, server trả về status 429 Too Many Requests cùng với headers RateLimit-Limit, RateLimit-Remaining, và RateLimit-Reset để client biết khi nào được gửi request tiếp.

📌 Ghi nhớ
Mặc định express-rate-limit lưu trạng thái trong memory của process. Khi deploy với nhiều instances (horizontal scaling), mỗi instance có counter riêng — dẫn đến rate limit không hoạt động đúng. Dùng rate-limit-redis store để chia sẻ counter qua Redis (đã học ở chương 14).

15.10 Input Validation với Joi hoặc Zod

Validate input ở mọi endpoint là bắt buộc — không bao giờ tin dữ liệu từ client. Có hai library phổ biến: Joi (mature, callback-style) và Zod (TypeScript-first, schema tái dùng với inferred types). Dưới đây là ví dụ với Joi: 

BashTerminal
npm install joi
JavaScriptvalidation/userSchemas.js
const Joi = require('joi');

const createUserSchema = Joi.object({
  name: Joi.string().min(2).max(100).required()
    .messages({ 'string.min': 'Tên phải có ít nhất 2 ký tự' }),
  email: Joi.string().email().required()
    .messages({ 'string.email': 'Email không hợp lệ' }),
  password: Joi.string().min(8).pattern(/^(?=.*[A-Z])(?=.*[0-9])/).required()
    .messages({
      'string.min': 'Mật khẩu phải có ít nhất 8 ký tự',
      'string.pattern.base': 'Mật khẩu phải có ít nhất 1 chữ hoa và 1 số'
    }),
  role: Joi.string().valid('user', 'admin').default('user')
});

const updateUserSchema = Joi.object({
  name: Joi.string().min(2).max(100),
  email: Joi.string().email(),
  phone: Joi.string().pattern(/^[0-9]{10,11}$/)
}).min(1); // Phải có ít nhất 1 field

module.exports = { createUserSchema, updateUserSchema };
JavaScriptmiddleware/validate.js
// Middleware factory: validate(schema) trả về middleware function
const validate = (schema, source = 'body') => {
  return (req, res, next) => {
    const { error, value } = schema.validate(req[source], {
      abortEarly: false,  // Gom tất cả lỗi, không dừng ở lỗi đầu tiên
      stripUnknown: true  // Xóa các fields không có trong schema
    });
    if (error) {
      const details = error.details.map(d => ({
        field: d.path.join('.'),
        message: d.message
      }));
      return res.status(422).json({
        success: false,
        error: {
          code: 'VALIDATION_ERROR',
          message: 'Dữ liệu không hợp lệ',
          details
        }
      });
    }
    req[source] = value; // Thay thế bằng data đã được validate và sanitize
    next();
  };
};

module.exports = validate;

💡 Mẹo
Dùng abortEarly: false để Joi thu thập tất cả lỗi validation trong một lần, thay vì dừng ở lỗi đầu tiên. Client nhận được toàn bộ danh sách lỗi trong một request, giúp họ sửa form nhanh hơn mà không phải submit nhiều lần.

Bài tập thực hành

Các bài tập dưới đây yêu cầu bạn tự triển khai các tính năng đã học. Khởi tạo một Express project mới với Mongoose và áp dụng từng pattern theo thứ tự.

Dễ

15.1 Field Selection Middleware

Thêm field selection vào GET /users: query param ?fields=id,name,email chỉ trả về các fields được chỉ định thay vì toàn bộ document. Gợi ý: dùng .select() của Mongoose với danh sách fields từ query string. Đảm bảo whitelist các fields được phép chọn (không cho phép chọn password hay __v).

Trung bình

15.2 Cursor Pagination

Implement cursor-based pagination thay cho offset pagination cho GET /posts (sort by _id giảm dần). Đảm bảo response có nextCursor và hasMore. Test với Postman: lấy trang đầu, copy nextCursor vào request tiếp theo, xác nhận không có item bị lặp hoặc bị skip. Xử lý edge case: cursor không hợp lệ hoặc đã là trang cuối.

Khó

15.3 API Versioning Demo

Build demo versioning hoàn chỉnh: v1 trả { name, email }, v2 thêm { phone, avatar, joinedAt }. Thêm header X-API-Version vào mọi response để client biết đang dùng version nào. Thêm Deprecation: true và Sunset: <date> header cho tất cả endpoints của v1. Document cả hai version với Swagger (hai server trong servers array của swagger config). Test với curl và verify headers.

Tổng kết chương 15

Chúng ta đã đi qua toàn bộ các best practices cốt lõi để thiết kế REST API chuyên nghiệp. Đây là bản tóm tắt nhanh những điểm quan trọng nhất:

Chủ đề Best Practice Anti-pattern cần tránh
URL Design Danh từ số nhiều, không có động từ /getUsers, /createPost
Status Codes Dùng đúng code theo ngữ cảnh Trả 200 cho mọi thứ kể cả lỗi
Response Format Nhất quán, có success flag và error.code Mỗi endpoint một kiểu format khác nhau
Pagination Luôn phân trang, giới hạn max limit Trả toàn bộ collection, không giới hạn
Versioning URL versioning rõ ràng, có deprecation policy Break changes mà không báo trước
File Upload Validate mimetype, giới hạn size, lưu cloud Accept mọi file, lưu thẳng trên local disk production
Documentation Swagger/OpenAPI, annotations ngay trong code Không có docs hoặc docs lỗi thời
Rate Limiting Giới hạn request, trả 429 với thông tin rõ ràng Không có giới hạn, để API bị abuse
Validation Validate mọi input, trả về tất cả lỗi cùng lúc Tin dữ liệu từ client, chỉ validate ở frontend
