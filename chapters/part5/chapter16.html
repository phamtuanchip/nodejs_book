Chương 16: Testing và Code Quality

Code không có test là code bạn không dám sửa. Test không chỉ bắt bugs — chúng là tài liệu sống, là mạng lưới an toàn giúp bạn refactor tự tin. Chương này xây dựng test suite đầy đủ.

🎯 Sau chương này bạn sẽ hiểu được
  • Phân biệt Unit Test, Integration Test, E2E Test
  • Setup Jest và viết tests từ cơ bản đến nâng cao
  • Mock dependencies để test độc lập
  • Integration test HTTP endpoints với Supertest
  • Đo lường test coverage và đặt threshold
  • Cấu hình ESLint và Prettier cho code quality

16.1 Tại sao cần Test?

Câu hỏi này nghe có vẻ đơn giản, nhưng nhiều lập trình viên vẫn bỏ qua testing vì áp lực deadline, hoặc vì nghĩ rằng "code nhỏ thì không cần test". Thực tế cho thấy điều ngược lại: chi phí sửa một bug tăng theo cấp số nhân theo thời gian bug tồn tại.

Chi phí của Bug theo thời gian

Một nghiên cứu nổi tiếng của IBM và nhiều tổ chức phần mềm lớn chỉ ra rằng chi phí sửa một bug phụ thuộc rất lớn vào thời điểm bug được phát hiện:

Giai đoạn phát hiện Chi phí tương đối Mô tả
Trong lúc dev viết code 1x Dev tự phát hiện ngay, sửa trong vài phút
Trong Code Review 5x Reviewer thấy, dev phải sửa lại và review lại
QA / Testing team 15x QA tạo ticket, dev fix, QA retest — mất nhiều ngày
Production (user phát hiện) 100x+ Hotfix khẩn cấp, downtime, mất dữ liệu, thiệt hại thương hiệu

Điều này có nghĩa là đầu tư thời gian viết tests ngay từ đầu là một quyết định kinh tế rất khôn ngoan. Một test suite tốt giúp bạn phát hiện bugs ngay khi chúng được tạo ra, với chi phí thấp nhất có thể.

Test là Documentation không thể Outdated

Tài liệu thông thường (README, wiki, comments) rất dễ bị lỗi thời. Khi code thay đổi, documentation thường không được cập nhật theo. Nhưng tests thì khác — nếu bạn thay đổi behavior của code mà không cập nhật tests, tests sẽ fail ngay lập tức. Điều này đảm bảo tests luôn phản ánh đúng hành vi thực tế của hệ thống.

Một bộ tests tốt có thể trả lời câu hỏi: "Hàm này làm gì với input này?" rõ ràng hơn bất kỳ comment nào. Khi một developer mới join team, đọc tests là cách nhanh nhất để hiểu codebase hoạt động như thế nào.

Refactor với Confidence

Đây là một trong những lợi ích lớn nhất của testing. Khi bạn có test suite đầy đủ, bạn có thể refactor code mạnh dạn hơn. Thay vì lo lắng "tôi đổi cái này liệu có break gì không?", bạn chỉ cần chạy tests và để chúng trả lời câu hỏi đó.

💡 Mẹo

Một quy tắc vàng: không bao giờ refactor mà không có tests. Nếu cần refactor một module chưa có tests, hãy viết tests trước (characterization tests — tests mô tả behavior hiện tại), rồi mới refactor.

Testing Pyramid

Martin Fowler đã phổ biến khái niệm Testing Pyramid — một mô hình hướng dẫn cách phân bổ các loại tests. Hình tháp có ba tầng, từ dưới lên trên:

  • Unit Tests (tầng đáy): Test từng hàm, module riêng lẻ. Nhanh, rẻ, nhiều nhất.
  • Integration Tests (tầng giữa): Test sự tương tác giữa các module, database, API. Chậm hơn, ít hơn.
  • E2E Tests (đỉnh): Test toàn bộ luồng từ UI đến database. Chậm nhất, đắt nhất, ít nhất.

Lý do tỉ lệ này được khuyến nghị: Unit tests cung cấp phản hồi nhanh nhất (chạy trong mili-giây), dễ debug nhất khi fail, và ít tốn kém nhất để viết và maintain. E2E tests thì ngược lại — chạy chậm (có thể mất nhiều phút), khó debug, và dễ bị flaky (đôi khi pass đôi khi fail không có lý do rõ ràng).

📌 Ghi nhớ

Testing pyramid chỉ là hướng dẫn, không phải quy tắc cứng nhắc. Tùy thuộc vào dự án, đôi khi tầng integration tests có thể chiếm tỉ lệ lớn hơn (ví dụ như các API-heavy backends). Mục tiêu là có đủ tests ở mỗi tầng để đảm bảo độ tin cậy.

16.2 Setup Jest

Jest là testing framework phổ biến nhất trong hệ sinh thái JavaScript/NodeJS, được phát triển bởi Meta (Facebook). Jest có đầy đủ mọi thứ cần thiết trong một package: test runner, assertion library, mocking, và coverage reporting — không cần cài thêm nhiều packages khác nhau như với Mocha/Chai/Sinon.

Cài đặt

Bashterminal
# Cài Jest và Supertest (dùng cho integration tests)
npm install --save-dev jest supertest

# Nếu dùng TypeScript
npm install --save-dev ts-jest @types/jest

# Kiểm tra version
npx jest --version

Cấu hình npm scripts

Thêm các scripts vào package.json để có thể chạy tests theo nhiều mode khác nhau: 

JSONpackage.json
{
  "scripts": {
    "test": "jest",
    "test:watch": "jest --watch",
    "test:coverage": "jest --coverage",
    "test:ci": "jest --ci --coverage --forceExit"
  }
}

Giải thích từng script:

  • jest: Chạy tất cả tests một lần rồi thoát.
  • jest --watch: Chế độ watch — tự động re-run tests khi file thay đổi. Rất hữu ích khi đang phát triển.
  • jest --coverage: Chạy tests và sinh báo cáo coverage.
  • jest --ci --coverage --forceExit: Mode dùng cho CI/CD. --ci tắt interactive mode, --forceExit đảm bảo process thoát sau khi tests xong (quan trọng khi có database connections chưa đóng).

jest.config.js

File cấu hình Jest cho phép bạn tùy chỉnh nhiều thứ — từ test environment, file patterns, đến coverage thresholds: 

JavaScriptjest.config.js
module.exports = {
  // Environment: 'node' cho backend (mặc định), 'jsdom' cho browser
  testEnvironment: 'node',

  // Pattern để tìm test files
  testMatch: [
    '**/tests/**/*.test.js',
    '**/__tests__/**/*.js'
  ],

  // Các file được tính vào coverage report
  collectCoverageFrom: [
    'src/**/*.js',
    '!src/index.js',         // Exclude entry point
    '!**/node_modules/**'
  ],

  // Ngưỡng coverage tối thiểu — build fail nếu dưới ngưỡng
  coverageThresholds: {
    global: {
      branches: 70,
      functions: 75,
      lines: 75,
      statements: 75
    }
  },

  // File chạy trước khi test suite bắt đầu (setup DB, global mocks...)
  setupFilesAfterFramework: ['./tests/setup.js'],

  // Verbose output để dễ đọc
  verbose: true
};
⚠️ Cảnh báo

Đặt coverageThresholds quá cao (ví dụ 100%) từ đầu có thể gây ra anti-pattern "test chỉ để đạt con số" thay vì test có nghĩa. Bắt đầu với 70-75% và tăng dần là chiến lược hợp lý.

16.3 Unit Testing Cơ Bản

Unit test kiểm tra từng đơn vị code nhỏ nhất (thường là một hàm) một cách độc lập. Mục tiêu là: với input X, hàm có trả về output Y đúng như mong đợi không? Unit tests không cần database, không cần network — chỉ cần logic của hàm đó.

Jest Matchers — Các phép kiểm tra phổ biến

Jest cung cấp rất nhiều matchers — các hàm kiểm tra (assertion) có cú pháp đọc gần như tiếng Anh tự nhiên:

Matcher Ý nghĩa Ví dụ
toBe(val) So sánh strict equality (===) expect(1 + 1).toBe(2)
toEqual(val) So sánh deep equality (cho objects/arrays) expect({a:1}).toEqual({a:1})
toContain(item) Array/string chứa item expect([1,2,3]).toContain(2)
toHaveLength(n) Array/string có độ dài n expect('abc').toHaveLength(3)
toThrow(msg) Hàm throw error expect(() => fn()).toThrow('err')
toBeTruthy() Giá trị truthy expect('hello').toBeTruthy()
toBeFalsy() Giá trị falsy expect(null).toBeFalsy()
toBeNull() Giá trị null expect(val).toBeNull()
toBeUndefined() Giá trị undefined expect(val).toBeUndefined()
toBeGreaterThan(n) Số lớn hơn n expect(5).toBeGreaterThan(3)
toMatch(regex) String khớp regex/substring expect('hello').toMatch(/ell/)
toHaveProperty(key) Object có property expect(obj).toHaveProperty('id')

Bạn có thể thêm .not vào trước bất kỳ matcher nào để đảo ngược: expect(val).not.toBeNull().

Ví dụ thực tế: Unit Test cho Utility Functions

Hãy bắt đầu với một module utility đơn giản gồm ba hàm: format tiền tệ, tạo slug từ text, và validate email: 

JavaScriptsrc/utils/format.js
// Hàm format tiền tệ Việt Nam
const formatCurrency = (amount) => {
  if (amount < 0) throw new Error('Số tiền không được âm');
  return new Intl.NumberFormat('vi-VN', {
    style: 'currency',
    currency: 'VND'
  }).format(amount);
};

// Hàm tạo slug từ text (kể cả tiếng Việt có dấu)
const slugify = (text) => {
  return text
    .toLowerCase()
    .normalize('NFD')
    .replace(/[̀-ͯ]/g, '')   // Xóa dấu
    .replace(/[^a-z0-9]+/g, '-')       // Thay ký tự đặc biệt bằng gạch ngang
    .replace(/^-|-$/g, '');             // Xóa gạch ngang đầu/cuối
};

// Hàm validate email
const validateEmail = (email) => {
  return /^[^\s@]+@[^\s@]+\.[^\s@]+$/.test(email);
};

module.exports = { formatCurrency, slugify, validateEmail };

Bây giờ viết tests cho module này. Mỗi hàm sẽ có một describe block riêng, bên trong là các it (hoặc test) blocks cho từng case: 

JavaScripttests/unit/format.test.js
const { formatCurrency, slugify, validateEmail } = require('../../src/utils/format');

// describe() nhóm các tests liên quan lại với nhau
describe('formatCurrency', () => {
  it('formats VND correctly', () => {
    // toMatch() cho phép kiểm tra string chứa pattern
    expect(formatCurrency(1000000)).toMatch(/1\.000\.000/);
  });

  it('handles zero', () => {
    expect(formatCurrency(0)).toMatch(/0/);
  });

  it('throws for negative values', () => {
    // Khi test hàm throw, phải bọc trong arrow function
    expect(() => formatCurrency(-100)).toThrow('Số tiền không được âm');
  });
});

describe('slugify', () => {
  it('converts Vietnamese text to slug', () => {
    expect(slugify('Xin chào thế giới')).toBe('xin-chao-the-gioi');
  });

  it('handles special characters', () => {
    expect(slugify('Hello World!')).toBe('hello-world');
  });

  it('removes leading/trailing dashes', () => {
    expect(slugify('  hello  ')).toBe('hello');
  });

  it('handles numbers in text', () => {
    expect(slugify('Chapter 16 Testing')).toBe('chapter-16-testing');
  });
});

describe('validateEmail', () => {
  it('validates correct email', () => {
    expect(validateEmail('user@example.com')).toBe(true);
    expect(validateEmail('name.last@domain.org')).toBe(true);
  });

  it('rejects invalid email', () => {
    expect(validateEmail('not-an-email')).toBe(false);
    expect(validateEmail('missing@tld')).toBe(false);
    expect(validateEmail('@domain.com')).toBe(false);
    expect(validateEmail('')).toBe(false);
  });
});

Lifecycle Hooks: beforeEach / afterEach / beforeAll / afterAll

Jest cung cấp các hàm lifecycle hooks để chạy code trước/sau tests. Hiểu rõ sự khác biệt giữa chúng rất quan trọng:

  • beforeAll(fn): Chạy một lần trước tất cả tests trong describe block. Dùng cho setup tốn kém như kết nối database.
  • afterAll(fn): Chạy một lần sau tất cả tests. Dùng cho cleanup như đóng kết nối database.
  • beforeEach(fn): Chạy trước mỗi test. Dùng cho reset state, tạo test data mới.
  • afterEach(fn): Chạy sau mỗi test. Dùng cho cleanup state, clear mocks.
JavaScripttests/unit/lifecycle-example.test.js
describe('Lifecycle Hooks Demo', () => {
  let db;
  let user;

  // Chạy 1 lần — kết nối database (ví dụ concept)
  beforeAll(async () => {
    db = await createTestDatabase();
    console.log('DB connected');
  });

  // Chạy trước MỖI test — tạo data sạch
  beforeEach(async () => {
    user = await db.users.create({
      name: 'Test User',
      email: 'test@example.com'
    });
  });

  // Chạy sau MỖI test — dọn dẹp data
  afterEach(async () => {
    await db.users.deleteMany({});
    jest.clearAllMocks(); // Reset tất cả mock function calls
  });

  // Chạy 1 lần sau tất cả tests — đóng kết nối
  afterAll(async () => {
    await db.close();
  });

  it('test 1 — user tồn tại', () => {
    expect(user).toBeDefined();
    expect(user.email).toBe('test@example.com');
  });

  it('test 2 — user được tạo mới (không bị ảnh hưởng từ test 1)', () => {
    // Mỗi test có user riêng nhờ beforeEach
    expect(user.name).toBe('Test User');
  });
});
💡 Mẹo

Dùng beforeEach thay vì beforeAll khi muốn đảm bảo mỗi test bắt đầu với state hoàn toàn sạch (test isolation). Tests phụ thuộc vào nhau là một anti-pattern nguy hiểm — thứ tự chạy tests có thể thay đổi.

16.4 Mocking với Jest

Một trong những thách thức lớn nhất khi viết unit tests là dependencies. Hàm của bạn có thể gọi database, gửi email, gọi API bên ngoài — những thứ này không nên thực sự chạy trong unit tests (chậm, không ổn định, có side effects). Đây là lúc mocking phát huy tác dụng.

Mocking là kỹ thuật thay thế một dependency thật bằng một "giả" (mock) có behavior do bạn kiểm soát. Jest có ba cơ chế mocking chính:

  • jest.fn(): Tạo một mock function từ đầu.
  • jest.spyOn(obj, 'method'): "Spy" lên một method có sẵn, theo dõi nó được gọi như thế nào mà không cần thay thế behavior (hoặc có thể override).
  • jest.mock('module'): Mock toàn bộ một module — mọi export của module đó đều trở thành mock function tự động.

Ví dụ 1: Mock External Service (Nodemailer)

Giả sử có hàm sendWelcomeEmail dùng Nodemailer để gửi email. Trong unit test, ta không muốn gửi email thật — ta chỉ muốn kiểm tra hàm gọi nodemailer đúng cách không: 

JavaScriptsrc/services/emailService.js
const nodemailer = require('nodemailer');

const sendWelcomeEmail = async (user) => {
  const transporter = nodemailer.createTransport({
    host: process.env.SMTP_HOST,
    port: 587,
    auth: {
      user: process.env.SMTP_USER,
      pass: process.env.SMTP_PASS
    }
  });

  await transporter.sendMail({
    from: '"MyApp" <noreply@myapp.com>',
    to: user.email,
    subject: `Chào mừng ${user.name}!`,
    html: `<h1>Xin chào ${user.name}</h1><p>Cảm ơn bạn đã đăng ký.</p>`
  });
};

module.exports = { sendWelcomeEmail };
JavaScripttests/unit/emailService.test.js
// jest.mock() PHẢI được gọi trước khi require module cần test
jest.mock('nodemailer');

const nodemailer = require('nodemailer');
const { sendWelcomeEmail } = require('../../src/services/emailService');

describe('sendWelcomeEmail', () => {
  let mockSendMail;

  beforeEach(() => {
    // Tạo mock function cho sendMail
    // mockResolvedValue() — mock async function trả về resolved Promise
    mockSendMail = jest.fn().mockResolvedValue({ messageId: 'test-id' });

    // Khi code gọi nodemailer.createTransport(), nó nhận object giả
    nodemailer.createTransport.mockReturnValue({
      sendMail: mockSendMail
    });
  });

  afterEach(() => {
    // Reset tất cả mock sau mỗi test để tránh ảnh hưởng chéo
    jest.clearAllMocks();
  });

  it('sends email to correct recipient', async () => {
    const user = { name: 'Alice', email: 'alice@test.com' };
    await sendWelcomeEmail(user);

    // Kiểm tra sendMail được gọi đúng 1 lần
    expect(mockSendMail).toHaveBeenCalledTimes(1);

    // expect.objectContaining() — kiểm tra object có các field này (có thể có thêm field khác)
    expect(mockSendMail).toHaveBeenCalledWith(
      expect.objectContaining({
        to: 'alice@test.com',
        subject: 'Chào mừng Alice!'
      })
    );
  });

  it('propagates send errors', async () => {
    // mockRejectedValue() — mock async function throw error
    mockSendMail.mockRejectedValue(new Error('SMTP error'));

    // Test async throw: dùng await + expect().rejects.toThrow()
    await expect(
      sendWelcomeEmail({ name: 'Bob', email: 'bob@test.com' })
    ).rejects.toThrow('SMTP error');
  });

  it('creates transporter with correct config', async () => {
    const user = { name: 'Alice', email: 'alice@test.com' };
    await sendWelcomeEmail(user);

    expect(nodemailer.createTransport).toHaveBeenCalledWith(
      expect.objectContaining({
        host: process.env.SMTP_HOST,
        port: 587
      })
    );
  });
});

Ví dụ 2: Mock Database Model

Trong unit tests cho service layer, ta không muốn thực sự kết nối MongoDB. Thay vào đó, ta mock Mongoose model để kiểm soát data trả về: 

JavaScripttests/unit/userService.test.js
// Mock toàn bộ module User model
jest.mock('../../src/models/User');

const User = require('../../src/models/User');
const userService = require('../../src/services/userService');

describe('userService', () => {
  afterEach(() => {
    jest.clearAllMocks();
  });

  describe('getUserById', () => {
    it('returns user when found', async () => {
      const mockUser = {
        _id: '507f1f77bcf86cd799439011',
        name: 'Alice',
        email: 'alice@test.com'
      };

      // Khi code gọi User.findById(), nó nhận mockUser thay vì query DB thật
      User.findById.mockResolvedValue(mockUser);

      const result = await userService.getUserById('507f1f77bcf86cd799439011');

      expect(result).toEqual(mockUser);
      expect(User.findById).toHaveBeenCalledWith('507f1f77bcf86cd799439011');
    });

    it('throws when user not found', async () => {
      User.findById.mockResolvedValue(null);

      await expect(userService.getUserById('999')).rejects.toThrow('User not found');
    });
  });

  describe('updateUser', () => {
    it('updates user fields', async () => {
      const mockUpdatedUser = {
        _id: '123',
        name: 'Alice Updated',
        email: 'alice@test.com'
      };

      User.findByIdAndUpdate.mockResolvedValue(mockUpdatedUser);

      const result = await userService.updateUser('123', { name: 'Alice Updated' });

      expect(result).toEqual(mockUpdatedUser);
      expect(User.findByIdAndUpdate).toHaveBeenCalledWith(
        '123',
        { name: 'Alice Updated' },
        { new: true, runValidators: true }
      );
    });
  });
});

jest.spyOn — Theo dõi mà không thay thế

Đôi khi bạn chỉ muốn theo dõi xem một method có được gọi không, mà không cần thay đổi behavior của nó. jest.spyOn() cho phép điều này: 

JavaScripttests/unit/spy-example.test.js
const logger = require('../../src/utils/logger');

describe('Spy Example', () => {
  it('logs error when operation fails', async () => {
    // Spy lên logger.error — không thay đổi behavior
    const logSpy = jest.spyOn(logger, 'error');

    // Thực thi logic gây ra error...
    await someServiceThatLogs();

    // Kiểm tra logger.error đã được gọi
    expect(logSpy).toHaveBeenCalled();
    expect(logSpy).toHaveBeenCalledWith(expect.stringContaining('Error:'));

    // Restore method về implementation thật
    logSpy.mockRestore();
  });
});
📌 Ghi nhớ

Luôn gọi jest.clearAllMocks() trong afterEach để reset mock call counts và implementations. Nếu không, mock state từ test trước sẽ "rò rỉ" sang test sau, gây ra kết quả không đoán trước được.

16.5 Integration Testing với Supertest

Integration tests kiểm tra sự phối hợp giữa nhiều thành phần: routes, middleware, service, và database. Thay vì mock mọi thứ, integration tests sử dụng một test database thật (hoặc in-memory database) để đảm bảo tất cả các thành phần hoạt động đúng khi kết hợp với nhau.

Supertest là thư viện cho phép test HTTP endpoints mà không cần start một HTTP server thật — nó tự xử lý việc binding port, gửi request, và nhận response.

Global Test Setup

      };

      // Đăng ký lần 2 với cùng email — phải fail

      expect(res.body.error.code).toBe('EMAIL_ALREADY_EXISTS');
    });
  });

  // ===== POST /api/v1/auth/login =====
  describe('POST /api/v1/auth/login', () => {
    // Tạo user trước mỗi test trong describe block này
    beforeEach(async () => {

16.6 Test Coverage

Test coverage (độ bao phủ test) đo lường phần trăm code đã được tests "chạm tới". Đây là metric quan trọng nhưng thường bị hiểu sai. Coverage cao không đảm bảo code chất lượng — một test chạy qua code mà không assert gì cũng tính vào coverage.

Các loại Coverage Metrics

Jest (dùng Istanbul/nyc bên dưới) theo dõi 4 loại metrics:

Metric Ý nghĩa Ví dụ
Statements % câu lệnh đã được thực thi const x = 1; là 1 statement
Branches % nhánh rẽ đã được test (if/else, ternary, switch) if (x) {...} else {...} có 2 branches
Functions % hàm đã được gọi ít nhất một lần Mỗi function/arrow function được đếm
Lines % dòng code đã được thực thi Giống statements nhưng tính theo dòng

Trong 4 metrics, Branches thường là khó đạt nhất vì mỗi điều kiện if/else tạo ra 2 nhánh. Nếu tests chỉ test happy path mà bỏ qua error cases, branches coverage sẽ thấp.

Đặt Coverage Threshold

Coverage threshold trong jest.config.js đảm bảo CI/CD pipeline fail nếu coverage giảm xuống dưới mức cho phép — một cơ chế quan trọng để bảo vệ chất lượng code theo thời gian: 

JavaScriptjest.config.js
module.exports = {
  coverageThresholds: {
    // Ngưỡng global cho toàn bộ codebase
    global: {
      branches: 70,
      functions: 75,
      lines: 75,
      statements: 75
    },
    // Có thể đặt ngưỡng riêng cho từng file/thư mục quan trọng
    './src/services/': {
      branches: 80,
      functions: 85,
      lines: 85,
      statements: 85
    }
  }
};
⚠️ Cảnh báo

Đừng chase 100% coverage. Một số code không cần test (configuration files, simple getters/setters). Quan trọng hơn là test critical paths: authentication logic, payment processing, data validation. Tập trung vào chất lượng tests, không phải số lượng.

📌 Ghi nhớ

70-80% là ngưỡng coverage hợp lý cho hầu hết dự án. Tăng dần theo thời gian khi team quen với TDD. Đừng đột ngột đặt 90% cho codebase cũ — sẽ tạo ra nhiều tests vô nghĩa chỉ để đạt số.

16.8 Test Database Strategy với MongoDB Memory Server

Một thách thức lớn khi integration testing với MongoDB là: bạn cần một database thật để test, nhưng không muốn test can thiệp vào data production hay development. Có ba chiến lược phổ biến:

  1. Dùng database riêng cho test: Simple nhưng cần MongoDB running, dễ bị conflicts khi nhiều người test cùng lúc.
  2. Docker container MongoDB: Isolated nhưng cần Docker setup và start/stop container.
  3. MongoDB Memory Server: Chạy MongoDB trong memory, không cần cài MongoDB. Khởi động nhanh, hoàn toàn isolated — đây là lựa chọn tốt nhất cho testing.

Cài đặt MongoDB Memory Server

Bashterminal
npm install --save-dev mongodb-memory-server

Test Database Helper

Tạo một helper module để tái sử dụng logic connect/disconnect/clear trong nhiều test files: 

JavaScripttests/helpers/testDb.js
const { MongoMemoryServer } = require('mongodb-memory-server');
const mongoose = require('mongoose');

let mongod; // MongoMemoryServer instance

/**
 * Khởi động in-memory MongoDB và kết nối Mongoose
 */
const connect = async () => {
  mongod = await MongoMemoryServer.create();
  const uri = mongod.getUri();

  await mongoose.connect(uri, {
    useNewUrlParser: true,
    useUnifiedTopology: true
  });
};

/**
 * Drop database, đóng kết nối, và dừng in-memory server
 */
const disconnect = async () => {
  await mongoose.connection.dropDatabase();
  await mongoose.connection.close();
  await mongod.stop();
};

/**
 * Xóa tất cả documents trong tất cả collections
 * (Dùng giữa các tests để đảm bảo isolation)
 */
const clearDatabase = async () => {
  const collections = mongoose.connection.collections;
  for (const key in collections) {
    await collections[key].deleteMany({});
  }
};

module.exports = { connect, disconnect, clearDatabase };

Hiểu rõ thứ tự chạy các lifecycle hooks giúp bạn đặt setup và teardown đúng chỗ. Đây là sơ đồ trực quan:

Tối ưu Performance cho Test Suite lớn

Khi test suite phát triển, thời gian chạy có thể tăng đáng kể. Một số kỹ thuật tối ưu: 

JavaScriptjest.config.js
module.exports = {
  // Chạy tests song song trên nhiều worker (mặc định = số CPU cores - 1)
  maxWorkers: '50%',

  // Chỉ chạy lại tests liên quan đến files đã thay đổi (khi dùng --watch)
  watchPlugins: [
    'jest-watch-typeahead/filename',
    'jest-watch-typeahead/testname'
  ],

  // Cache transform results để lần chạy sau nhanh hơn
  cache: true,
  cacheDirectory: '.jest-cache',

  // Timeout cho mỗi test (mặc định 5000ms)

};

Bài tập thực hành

Sau đây là các bài tập giúp bạn củng cố kiến thức từ chương này. Mỗi bài được đánh giá độ khó để bạn lên kế hoạch học tập phù hợp.

16.1 Test CRUD Routes

Viết integration tests cho tất cả routes của Posts API: GET /api/posts (lấy danh sách), GET /api/posts?tag=nodejs (lọc theo tag), GET /api/posts?page=2&limit=5 (pagination). Mỗi test case cần kiểm tra: status code trả về đúng, cấu trúc response có đủ fields cần thiết (success, data, pagination), và dữ liệu trả về khớp với data đã tạo. Tạo ít nhất 3 posts với các tags khác nhau làm test data trước khi test.

Trung bình

16.2 Mock Email Service

Mock nodemailer.sendMail() trong unit tests để test email flow mà không gửi email thật. Cụ thể: (1) Viết unit test xác nhận email được gọi với đúng recipient và subject khi user đăng ký mới. (2) Viết test cho trường hợp SMTP server fail — đảm bảo error được propagate và user không được tạo nếu email fail. (3) Viết test kiểm tra nội dung HTML email có chứa tên của user. Dùng jest.mock('nodemailer') và expect.objectContaining().

Khó

16.3 CI Pipeline với GitHub Actions

Setup CI test pipeline hoàn chỉnh với GitHub Actions: (1) Tạo .github/workflows/ci.yml để chạy tests tự động khi push hoặc tạo PR vào main/develop. (2) Pipeline phải fail PR nếu coverage dưới 70% ở bất kỳ metric nào. (3) Chạy ESLint check trong CI — fail nếu có errors. (4) Cache node_modules để tăng tốc CI. (5) Tạo coverage badge trong README bằng Shields.io hoặc Codecov. Thêm environment variables cần thiết vào GitHub Secrets.
